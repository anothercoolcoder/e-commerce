Actúa como un ingeniero senior de Java/Maven/JavaFX especializado en refactorización académica y testing.

Estoy trabajando en un proyecto universitario de Programación III llamado ShopTree. El proyecto ya está avanzado y fue desarrollado parcialmente por otro compañero. Tu trabajo NO es rehacer el proyecto desde cero, sino revisar cuidadosamente el código existente, entenderlo y dejarlo lo más simple, coherente y fácil de explicar posible, sin romper los requisitos académicos ni la funcionalidad existente.

IMPORTANTE:

* No agregues complejidad innecesaria.
* No introduzcas patrones, librerías o abstracciones solamente porque sean "best practice".
* No conviertas un proyecto académico en una arquitectura empresarial.
* Prioriza código que un estudiante pueda explicar claramente frente al profesor.
* Antes de modificar cualquier cosa, entiende cómo funciona actualmente.
* No elimines funcionalidad requerida solamente para reducir código.
* No inventes requisitos que no estén en el proyecto.
* Conserva las estructuras de datos exigidas por el proyecto.
* Si encuentras código innecesariamente complejo, duplicado o difícil de explicar, simplifícalo.
* Si una clase está bien como está, no la modifiques por gusto.

3. SEGUNDA FASE: SIMPLIFICACIÓN
===============================

Después de entender el proyecto, refactoriza.

Objetivo principal:

"El código debe ser lo más sencillo posible de leer, entender, probar y explicar, manteniendo la funcionalidad."

Prioridades:

1. Eliminar duplicación.
2. Eliminar código muerto que realmente no sea necesario.
3. Reducir métodos excesivamente largos.
4. Reducir clases innecesariamente complejas.
5. Evitar abstracciones innecesarias.
6. Evitar patrones de diseño artificiales.
7. Mantener nombres claros.
8. Mantener responsabilidades claras.
9. Mantener las estructuras de datos requeridas.
10. Mantener una arquitectura que pueda explicarse fácilmente.

Ejemplo de criterio:

Si una solución puede hacerse con:

Producto → Controller → Repository

no crear:

Producto → DTO → Mapper → Service → Facade → Adapter → Repository

a menos que exista una razón real o un requisito académico que lo justifique.

No elimines DTO, Mapper, Service, Repository, árboles, etc. automáticamente. Primero verifica si realmente son utilizados o requeridos.

8. JACOCO — PARTE CRÍTICA
=========================

Este punto es obligatorio.

El profesor exige una cobertura mínima del 75 % en la lógica de negocio.

No te limites a ejecutar JaCoCo y decir "hay X %".

Debes comprobar exactamente:

1. Qué plugin de JaCoCo está configurado en pom.xml.
2. En qué fase del ciclo Maven se ejecuta.
3. Qué tests ejecuta.
4. Qué clases incluye.
5. Qué clases excluye.
6. Si está generando correctamente el reporte.
7. Si existe un threshold/check de cobertura.
8. Qué métrica utiliza ese threshold:

   * instruction
   * branch
   * line
   * method
   * class
9. Si el threshold realmente corresponde al requisito del profesor.
10. Si la cobertura del 75 % se está calculando sobre la lógica de negocio y no simplemente sobre todo el proyecto incluyendo JavaFX, DTOs, getters/setters, configuración, etc.

IMPORTANTE:

No manipules JaCoCo para inflar artificialmente la cobertura.

No excluyas clases de lógica de negocio únicamente para alcanzar 75 %.

Sí puedes excluir legítimamente código que no constituye lógica de negocio, por ejemplo:

* clases de arranque
* configuración
* clases generadas
* código puramente visual
* DTOs simples
* clases que el profesor explícitamente no considere lógica de negocio

Pero cada exclusión debe tener una razón clara.

9. CONFIGURACIÓN DE JACOCO
==========================

Determina si la configuración actual debería ser algo equivalente a:

* preparación del agente antes de tests
* ejecución de tests
* generación del reporte
* verificación del mínimo de cobertura

Comprueba que:

mvn clean test

produzca correctamente los resultados de JaCoCo.

También comprueba:

mvn clean verify

si el proyecto está configurado para validar cobertura durante verify.

Si actualmente JaCoCo solamente genera un reporte pero NO hace fallar el build cuando se está por debajo del mínimo requerido, determina si eso debe corregirse.

El objetivo académico debe ser:

Si la cobertura de la lógica de negocio es menor al 75 % → Maven debe poder detectarlo.

Si está por encima → build correcto.

No cambies el umbral a un valor menor para que el proyecto pase.
